01 Summary

This document captures the design changes applied to the Medical Chronology screen and the rationale behind each decision. It is written for the engineers who will implement the views in production code. Examples reference the interactive prototype at the top of this page.

There are two primary states for any visit record on this screen:

  • Read view — the default. A visit card displays its extracted fields and AI confidence indicator.
  • Edit view — opened when the user clicks the pencil icon on a visit. A split layout exposes the source PDF on the left and an editable form on the right.

02 Scope of changes

What was changed

  • Added the EDITING pill anchored to the top-left of the editable card so the user always knows which visit they are editing.
  • Removed the green check (✓) and red X (✕) icon buttons from the edit-mode header — they duplicated the Save Changes / Cancel buttons at the bottom of the form.
  • Converted all static field rows in the edit view into real <input> and <textarea> elements with floating labels, focus states, and a green focus ring.
  • Added a footer action bar inside the editable card with explicit Save Changes (primary) and Cancel (secondary) buttons.
  • Wired the pencil icon, the close buttons, and the SHOW DOCS / HIDE DOCS tabs to toggle between read and edit modes.
  • Added a Check Design Specs button in the app's top bar that brings the reader to this section.

What was NOT changed (intentionally)

  • Read-view card layout, including its green outline, type chip, date chip, Ai badge, and confidence pill.
  • Top navigation, tabs, and the "Last modified by" bar.
  • Toolbar (search, filters, sort, export, Add Visit).
  • Document panel UI on the left side of the edit view (toolbar, page navigation, sidebar icons).

04 Read view

A visit record is rendered as a single card with a thin green border (#2BA875, 1.5px). Card padding is 26px / 32px (vertical / horizontal). Border radius is 12px.

Anatomy (top to bottom)

  • Header row: type chip (black background, white text), date chip with calendar icon, then right-aligned cluster of Ai badge, Confidence pill, pencil icon, trash icon.
  • Body rows with leading icon (building / id-badge) and "Label: value" content.
  • "Description" label followed by a bulleted list (• unicode bullets, 22px font, 1.65 line-height).
  • "View more" link in brand green (#1F8A5F).
  • Footer separated by a 1px top border: file reference (file icon, name, "Pages: N-M"), and a right-aligned "View Details" with eye icon.
Why the pencil triggers edit, not the whole card: Clicking the card body is reserved for future "expand to read full record" behaviour. Edit is a destructive, focused action that demands an explicit affordance — the pencil. Same pattern as Gmail, Notion, and Linear.

05 Edit view

Layout: a split-screen with the original PDF on the left and the editable form on the right. The full-app sidebar collapses in edit mode to maximize horizontal space for both panels. The top tabs and "Medical Chron & Timeline Draft" sub-tab remain visible so the user keeps navigational context.

5.1 Left panel — PDF document viewer

  • Header with filename and an X button to close the editor.
  • Toolbar: first / prev / next / last page, page number input, zoom out / in, more menu.
  • Left rail icons: thumbnails, bookmarks, sidebar toggle.
  • Viewport renders the redacted PDF pages with shadow + 1px border per page.
  • Vertical HIDE DOCS tab on the right edge of this panel closes the editor.

5.2 Right panel — editable form

The card uses a subtle green tint (rgba(43,168,117,0.04)) and a 14px top margin. The EDITING pill is absolutely positioned at top: -12px; left: 18px — sitting on the card's rounded top-left corner, above the first field's floating label.

EDITING pill specs:

  • Background: #2BA875
  • Text: white uppercase, 11px / weight 700 / letter-spacing 0.8px
  • Padding: 4px 12px
  • Border radius: 9999px (fully rounded)
  • Shadow: 0 2px 6px rgba(43,168,117,0.35)

Form fields (top to bottom)

  • Record Type — text input. Max-width 260px.
  • Date — text input with right-aligned calendar icon. Width 200px. Production: replace with a date picker.
  • Ai badge + Confidence pill (read-only, AI metadata).
  • Facility — text input with leading building icon.
  • Doctor / Provider — text input with leading id-badge icon.
  • Description — multi-line textarea, min 220px, max 360px, vertical resize allowed.
  • Page Reference — compact text input (130px wide).
  • Footer action bar — Save Changes (primary, green) and Cancel (secondary, white outline).

Type & spacing

  • Font: system stack. Engineers should map this to the existing app token if one exists.
  • Base size: 14px. Card body: 15px. Floating labels: 11px. Section labels: 12–15px.
  • Border radius: 10px on inputs / buttons / toolbar items; 12px on cards; 9999px on pills.
  • Box shadow: on the EDITING pill only — 0 2px 6px rgba(43,168,117,0.35). No shadows on cards or inputs in default state.

07 Behaviour notes for production

  • Dirty-state detection: track whether any input value differs from its initial value. When dirty and the user attempts to Cancel / close the PDF / HIDE DOCS, show a confirm modal ("Discard unsaved changes?").
  • Save flow: validate required fields (Record Type, Date, Facility, Provider), POST the diff to the backend, optimistically update the card in the list, refresh "Last modified by" and timestamp.
  • Concurrency: if another user has edited the same record between read and save, the API should return a conflict and the UI should surface a "This record was updated by {user}" warning with a refresh option.
  • Date input: use the existing in-house date-picker component (not the native browser one) so styling matches.
  • Description field: production should support paste-from-PDF cleanup (strip page numbers / repeated headers / soft-hyphen line breaks). Out of scope for this design pass.
  • Keyboard: Esc cancels (with dirty confirm if needed). Cmd/Ctrl+S triggers Save Changes. Tab order: Record Type → Date → Facility → Provider → Description → Page Reference → Save → Cancel.
  • Accessibility: every input has an associated label. Icons are decorative SVGs marked aria-hidden. Icon-only buttons (pencil, trash, close) carry aria-labels and tooltips.
  • Mobile / narrow viewport: at <1100px the split becomes stacked (PDF above form). At <760px the toolbar wraps and the SHOW/HIDE DOCS rail is hidden.
